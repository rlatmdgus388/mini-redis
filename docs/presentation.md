# Mini Redis 발표 개요

슬라이드 한 장이 `##` 하나다. 성능 수치는 측정(#18~#21)이 끝나면 채운다. **측정 전 수치는 쓰지 않는다.**

## 1. 무엇을 만들었나
- 해시테이블을 직접 구현한 인메모리 키-값 저장소, HTTP API
- 목표: 느린 API 앞에 캐시로 붙여 성능 차이를 **숫자로** 보여주기
- 한 문장: "DB가 창고라면 Redis는 책상 서랍"

## 2. 사용 패턴: cache-aside
1. GET → 있으면(hit) 바로 반환
2. 없으면(miss) 원본 API(200ms) 호출 → TTL과 함께 SET → 반환
- 데모: 같은 요청을 두 번 보내 두 번째가 빨라지는 것

## 3. 알려진 한계 (먼저 밝힌다)
1. O(N) 작업(리사이즈·prefix 삭제·KEYS·스냅샷 복사) 동안 모든 요청이 멈춘다
2. 명령이 한 번에 하나라 코어를 여러 개 못 쓴다 (GIL, 워커 1개)
3. 죽으면 최대 약 1초치 쓰기를 잃는다
4. 시스템 시계가 바뀌면 만료가 틀어진다
5. 무효화된 옛 키는 TTL까지 메모리를 차지한다
- 각 한계가 **어떤 선택의 대가인지**와 **어느 측정으로 크기를 보였는지**를 같이 말한다 (#20)

## 4. 해시테이블 (#2)
- 체이닝, FNV-1a 64비트, load factor 0.75 초과 시 2배
- 내장 `hash()`를 안 쓴 이유: 프로세스마다 값이 달라 재현 불가
- 리사이즈는 한 번에 O(n) → 스트레치: 점진적 리해싱(#24)

## 5. 동시성: 전역 락 (#3)
- `RLock` 하나, 명령이 원자적, Redis의 직렬 실행과 같은 효과
- 대안(버킷 락)이 어려운 이유: 리사이즈, 여러 키에 걸친 명령. Python은 GIL이라 이득도 적음 → 스트레치(#27)에서 비교

## 6. 만료: lazy + 타이밍 휠 (#7, #8)
- 접근하면 지운다(lazy) + 아무도 안 읽는 키는 휠이 회수
- 낡은 휠 항목은 꺼낼 때 무시 → 취소 연산이 필요 없다
- 비교 자료: 시간에 따른 남은 만료 키 수 (#21)

## 7. Lease: 스탬피드와 stale set (#10)
- 인기 키가 만료되는 순간 동시 100요청 → 원본 호출 수 비교 (#19)
- DEL과 늦은 PUT 경합 → 낡은 값이 다시 써지는지 비교 (#19)
- 출처: Facebook memcache (NSDI 2013)

## 8. 영속성: 스냅샷 + AOF (#12~#14)
- 쓰기는 AOF에 덧붙이고 1초마다 fsync, 주기적으로 스냅샷 후 AOF 비우기
- 디스크 I/O는 락 밖에서
- 데모: 서버 종료 후 재시작해도 데이터가 남는 것
